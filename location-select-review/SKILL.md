# 報修地點欄位下拉選單變更檢查 Skill

## 使用時機
當任務涉及以下內容時使用本 Skill：
- 修改前台報修表單（`index.html`）的地點輸入控制項（將 `<input>` 改為 `<select>`）
- 設定或調整地點下拉選單的選項內容與預設提示項目
- 驗證表單未選擇地點（`value=""`）時的前端必填阻擋機制
- 驗證後端 API（`app.py` 的 `/api/tickets` 等）對於地點資料的接收與 `missing` 欄位驗證
- 檢查管理後台頁面（`admin.html`）與案件列表 API 是否能正確呈現選取的地點名稱
- 設計或執行「報修地點下拉選單化」功能變更的測試案例

## 執行流程
1. 讀取軟體規格書，確認本次變更範圍僅限於「前台地點欄位改為下拉選單」，且不包含詳細樓層選項。
2. 檢查前台 `index.html`：確認 `location` 欄位已由 `<input>` 改為 `<select>`，並包含 `value=""` 且顯示「請選擇地點」的預設停用/提示選項，以及定義好的校園建築物選項清單（如行政大樓、圖書館、管理學院等）。
3. 檢查後端 `app.py`：確認接收 POST 請求時保留原有的字串接收與缺少欄位（missing）驗證機制，回傳正確狀態碼與案件編號（如 `T-XXX`）。
4. 檢查後台 `admin.html` 與相關 API：確認舊有資料與新建案件的地點名稱均能正常顯示。
5. 對照驗收條件（AC-01 至 AC-04），設計並執行測試案例，涵蓋未選擇地點阻擋、正常選擇送出與後台顯示。
6. 將檢查結果分類為「通過」、「需要修改」與「需要人工確認」。

## 輸出格式
檢查結果：通過／需要修改／需要人工確認

對應規格：
- FR-01: 前台報修表單 (`index.html`) 地點欄位改為 `<select>` 下拉選單並提供預設選項。
- FR-02: 下拉選單包含預設提示選項（`value=""`），配合前端必填驗證。
- FR-03: 後端 (`app.py`) 維持字串接收與 missing 驗證邏輯。
- FR-04: 後台與清單列表 (`admin.html`, `/api/tickets`) 能正常顯示選取之地點名稱。

受影響範圍：
- 前端頁面：`index.html`（報修表單地點欄位）、`admin.html`（後台列表顯示）
- 後端 API：`app.py`（`POST /api/tickets` 接收與驗證、`GET /api/tickets` 清單回傳）
- 資料欄位：`location`（格式為固定選項字串）

測試案例：
1. 輸入：開啟 `/` 頁面，點擊「地點」下拉選單
   預期結果：展開選單，包含預設提示「請選擇地點」及預定義之校園地點選項（行政大樓、圖書館等）。
2. 輸入：未選擇地點（維持「請選擇地點」），填寫其他欄位後點擊「送出報修」
   預期結果：前端攔截送出並跳出提示（如「請填寫：地點」），不發送請求。
3. 輸入：選擇合法地點（如「圖書館」）並填妥其他欄位，點擊「送出報修」
   預期結果：系統顯示建立成功訊息，後端回傳 201 狀態碼與案件編號（如 T-001）。
4. 輸入：成功送出案件後，切換至後台 `/admin` 或呼叫 GET API
   預期結果：該筆案件之地點欄位正確顯示「圖書館」。

需要人工確認：
- 地點下拉選項清單是否涵蓋所有實際需要支援的校園建築物。
- 舊有歷史資料（若包含樓層或自由輸入格式）在後台列表顯示時是否受到版面影響。

## 不可忽略的事項
- 必填驗證必須確保預設提示選項的 `value` 為空字串（`value=""`），否則會導致未選擇時仍可成功送出。
- 本次規格僅涵蓋建築物層級選項，不得自行擴充樓層選單邏輯。
- 不得修改後端既有的案件編號生成格式與狀態定義（待處理／處理中／已完成）。
- 不得將「需要人工確認」的項目（如選單文字是否符合校園習慣）直接標示為通過或完成。
